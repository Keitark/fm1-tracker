# Stock startup versus the SDK candidate

Offline review, 2026-09-27. No device operations. This is a comparison of
instructions, not proof that the replacement image boots.

Stock source is the hash-pinned `FM-1_010` application documented in
`STOCK_BOARD_PROFILE.md`. Candidates are the local SDK-linked headless and
peripheral images; use each build folder's symbols/disassembly for addresses.

## Common startup sequence

Stock entry `0x02000120` branches to `0x02000124`. It establishes SP/SSP,
initializes boot information, clears internal-RAM BSS, copies initialized
internal RAM from XIP, handles zero-sized external-memory areas, configures
cache/memory, gets update status, and enters the main runtime.

The SDK candidate follows that broad order. Its RAM addresses, sizes, stacks
and main-entry address must be generated by its own linker, not copied from
stock. `audit_boot.py` checks those relationships. A shared XIP entry is only
one part of compatibility.

## Bootloader argument comparison

The stock initializer is `0x020001e6..0x02000216`. Locate the SDK candidate's
`boot_info_init` in its generated symbols after each rebuild.
Both take a bootloader-provided pointer in r0 and copy these common fields:

| Source | Internal boot-info offset | Size |
|---|---:|---:|
| argument + 4 | +16 | 8 bytes |
| pointer at argument + 0, then pointee + 8 | +24 | 4 bytes |
| same pointee + 13 | +0 | 1 byte |
| argument + 12 | +28 | 2 bytes |
| argument + 14 | +30 | 2 bytes |
| argument + 16 | +32 | 8 bytes |

The internal destination differs: stock `0x01c7fd50`, SDK `0x01c7fd4c`.
That difference is **not by itself an input-ABI mismatch**: these are internal
storage locations. Do not relocate SDK state blindly to match stock.

However, the SDK additionally reads argument **+80 for 8 bytes** into
`sdram_info`, and **+88 for 4 bytes** into `ex_app_info`. Stock's initializer
does not read these extensions. SDK also writes the argument's +12 halfword
to `0x01c7ff0c`. These occur even in the current no-SDRAM candidate; disabling
SDRAM in application configuration did not remove the reads.

This proves a difference in what the initializers consume, **not** that the
bootloader supplies only 24 bytes or that a crash is inevitable.

## Recovered bootloader handoff and compatibility bridge

`tools/jieli-wl82/audit_stock_bootloader.py` decodes only the hash-pinned
backup's uncompressed boot bank. Directory, bank-header and code CRCs pass.
The bank loads at `0x01c02000`, has 14,368 code bytes, and SHA-256
`fcaf033c5e10526353ecb11279a7556ac8645026d370c0267912cb4bfa7c7e4d`.
No configuration/reserved extraction, chip-key handling or device access is
performed by that script. Its synthetic ELF is for analysis, not flashing.

Reviewed instructions establish:

- `0x01c04dc0`: r10 is `0x01c7fd80`.
- `0x01c051d0..0x01c051de`: the bootloader copies six words to
  r10+0x88, giving argument address `0x01c7fe08`.
- `0x01c051e0..0x01c051ec`: the first word points to argument+24;
  32 bytes of flash-header data are copied there.
- `0x01c05284..0x01c0528c`: r0 receives this argument and an indirect
  call transfers control to the application's entry.
- The write to argument+80 at `0x01c04fa8` is conditional on a metadata
  pointer. Initialization of +88 has not been established. This is not proof
  that no other path or mask-ROM stage initializes those locations.

Both local build profiles now link `boot/boot_compat.c` using
`--wrap=boot_info_init`. The bridge copies exactly the confirmed 24-byte
prefix into a 92-byte stack buffer and zeros the remainder. It preserves
the original flash-header pointer and calls the unmodified SDK initializer.
Thus the SDK retains its own boot-info layout and ROM-facing halfword write,
but receives zero SDRAM configuration and zero external-app base. The SDK
header `include_lib/system/boot.h` defines those extra fields; this build
has neither SDRAM nor external-app mounting. Compile-time guards prevent
using the bridge with either feature enabled.

The bridge runs after SP/SSP setup but before BSS/data initialization. Its
reviewed 54-byte machine code uses only volatile word loops, a 92-byte stack
buffer and the SDK initializer call: no initialized globals or libc helpers.
The audit checks the actual startup call target, every bridge instruction
except its relocated call displacement, and that call's SDK destination.
Host tests check zero extensions, unchanged input, repeatability and (Windows)
a 24-byte source at a read-only page boundary followed by a no-access page.
Negative ELF tests reject both a source-overread change and bridge bypass.
These are offline checks, **not** proof of physical boot.

`boot_init_after_ram_ready` is an empty return in the current candidate. Both
initializers run before the ordinary application BSS/data initialization;
replacement code there cannot rely on initialized application globals.

## Display and audio observations relevant to startup

- Display transport setup precedes a 100 ms wait, sleep-out, a 120 ms wait,
  the recovered register table, a black fill, and display-on. There is no
  established panel-reset GPIO pulse in this traced branch. Absence does not
  establish an electrical reset tie or behavior after a warm boot.
- The table's page window is 40..279. The later stock black-fill helper
  `0x02021600` sends 0..240 for both axes, then writes 115,200 zero bytes.
  This is not evidence that the visible origin is 0: the inclusive endpoint
  and transfer length do not describe a full 241-by-241 rectangle. Preserve
  offset uncertainty rather than copying this blindly into rendering.
- Stock audio initializes a countdown to `0xac56` (44,118 frames). The refill
  path reduces it by 64 and holds gain at zero while it was positive. Thus
  the actual hold is **690 halves / 44,160 frames**, then Q7 gain rises by one
  per half until 127. At our requested 44,100 Hz this is about 1.001 seconds
  of silence and 0.184 seconds to reach 127/128 gain. Stock's physical sample
  rate has not been measured.
- The recovered stock output table maps zero input to zero output. The NES
  adapter now reproduces the hold/ramp timing and linear Q7 multiplication,
  **not** stock's synthesizer processing or nonlinear output table. It still
  needs the board service contract; digital zero is not hardware amplifier
  mute and does not qualify rail sequencing or analog turn-on transients.

## Checks and unresolved gates

`tests/verify_stock_board.py` pins the stock bytes for the common boot fields
and audio countdown/ramp, as well as previously recovered routes/tables.
Host tests cover the full hold/ramp, signed-24 extrema, negative rounding,
output bounds, saturation at the final gain and restart. The adapter accepts
only the configured 512-byte callback geometry, so malformed callbacks cannot
advance the countdown.

Still required: physical boot/handoff validation, SDK initcall/storage
side-effect review, reviewed packaging/recovery and staged physical qualification.
Real SDK timing/IRQ services and a separate integrated peripheral boot link now
exist; see `PERIPHERAL_BOOT.md`. Both profiles remain `flashable: false`.
